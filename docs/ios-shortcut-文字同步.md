# iOS 快捷指令：文字同步

手机与电脑之间对剪贴板文字做**双向轮询同步**：手机复制了东西就上行到电脑；
电脑那边有新内容就写回手机剪贴板。它靠「App 打开时运行」的自动化反复进入，
不是一次性动作。

手机端只需导入 `文字同步.shortcut` 这一份。

## 目录结构

```
shortcuts/
├── lib/                     ← 所有快捷指令共用的部分（见 获取同步 那份文档）
└── 文字同步/
    ├── build.py             生成器（改逻辑改这里，别手改 plist）
    ├── 文字同步-unsigned.plist   生成物（未签名，别直接导入 iOS）
    └── 文字同步.shortcut          已签名，导入手机的就是它
```

## 日常操作

```bash
python shortcuts/文字同步/build.py                                            # 生成 plist
python shortcuts/lib/verify.py shortcuts/文字同步/文字同步-unsigned.plist      # 校验
python shortcuts/lib/sign.py shortcuts/文字同步/文字同步-unsigned.plist        # 签名
```

`verify.py` 现在能打印轮询型动作（电池 / Wi-Fi / 剪贴板 / 存储内容 / 可达性 /
计算表达式 / 运行快捷指令）和条件码（小于 / 小于等于 / 有任何值 …），多条件的
「任一 / 全部」也会逐条展开成「A 或 B」「A 且 B」；还多了一项「条件缺参数」，
专门抓「如果」里缺比较值、数值比较缺数值、以及把存在性判断写成单条件这三种会
在真机上标红的形态。当前产物：156 个动作，断裂引用 `none`，控制流异常 `none`，
条件缺参数 `none`。

## 一轮做什么

```text
前台 App 在名单里？（快捷指令/备忘录/豆包/微信/文件/信息/Chrome/Filebar/Google/Safari浏览器/QQ）
  └ 不在 → 整段跳过，一个请求都不发（省电的第一道闸）
推一次日志：地址 / 重复 / 间隔 / 通知 / 续跑 / 设备名
守卫（电量 ≤ 电量 / 没连 Wi-Fi / 电脑端不可达）
  └ 任一命中 → 记一行（电量、可达、网络明细）→ 停止
读缓存（上次对齐到的内容，一段文本）
重复 N 次：
  还在前台 App 里？离开（回桌面 / 被挂起）→ 停
  探活 /status：不可达 → 停（别让下一条请求抛错中断）
  读剪贴板（另取一份「文本」形态，后面全按文本比）→ 项目类型
    文本 / URL / 多信息文本：
        和缓存不同 → POST /ios/sync（上行，服务端据此广播）；缓存记成本地
        相同       → GET  /ios/latest（纯拉取）
    其它（图片 / 文件 / 空）→ GET /ios/latest
  服务端给了 content → 缓存 = 这段 content
  给了 content 且 和剪贴板不同 → 通知（可选）+ 写入剪贴板
  落一次缓存
  推一次日志（把这一轮的行带上）
  剩余轮次 ≤ 10 且「续跑」= 开 → 自调用一次 + 停止
  等待：前 1 分钟 时间1，1–3 分钟 时间2，3 分钟后 时间3（按累计等待时长选档）
推一次日志（收尾）
```

## 配置词典

快捷指令开头有「配置」词典，导入后可在 App 里直接改：

| 键 | 默认 | 说明 |
|---|---|---|
| `协议` | `http` | |
| `主机` | `192.168.1.23` | 电脑端地址，与 `config/server_config.json` 的 `host` 一致（旧手工包写的是 `.24`，是更早的地址） |
| `端口` | `8000` | 服务端口 |
| `密钥` | `123456` | 与电脑端 `server_config.json` 一致；进请求头 `key` |
| `电量` | `40` | 电量 ≤ 此值就不跑（百分比，不带 %） |
| `重复` | `40` | 跑几轮。**一轮 = 一次请求 + 一次等待**，不是一次请求。40 轮 ≈ 3s×20 + 5s×20 = 160 秒。它同时是续跑的基准：`剩余 = 重复 - 轮次` |
| `时间1` | `3` | 累计等待 0–60 秒 时的等待间隔（秒），默认 40 轮里约前 20 轮用这档 |
| `时间2` | `5` | 累计等待 60–180 秒 时用，默认 40 轮里后 20 轮用这档 |
| `时间3` | `10` | 累计 ≥ 180 秒 之后用（降频省电）。默认 40 轮到不了 180 秒，这档等于留给「重复 ≥ 45」的 |
| `通知` | `关` | 开 = 从电脑拿到新内容、真要写剪贴板时弹一条；关 = 静默写剪贴板 |
| `续跑` | `关` | 开 = 剩余 ≤ 10 轮时调用自己另起一份接着跑；关 = 跑满就结束。**开时 `重复` 必须 ≥ 12**，见下 |
| `调试` | `关` | 开 = 过程 POST 到 `/ios_log`，写 `log/ios_shortcut.log` |

### 续跑是什么

一句话：**这一份快用完了，让它用「运行快捷指令（自己）」再起一份，把寿命接上。**

判据在每轮末尾、等待之前算一次：`剩余 = 重复 - 当前轮次`，`剩余 ≤ 10` 就调用自己，
然后本份 `exit`。默认 40 轮 → 第 30 轮触发。默认关。

| | 关（默认） | 开 |
|---|---|---|
| 寿命 | 跑满 40 轮结束，约 160 秒 | 每约 160 秒续一次，条件一直成立就一直续 |
| 下次怎么进 | 靠自动化「打开 App 时」再进 | 自己接上，不用等自动化 |
| 观感 | 在微信里待超过 3 分钟，后半段就不同步了 | 待多久同步多久，近似常驻 |
| 省电 | 更省 | 长时间前台会持续发请求 |

续跑起的新一份会**重过白名单和守卫**，所以电量低、断网、切到桌面时链子自己断，
不会在后台空转。跑到第 30 轮续跑时不会先空等那 3 秒 —— 触发点放在等待之前。

⚠ **开续跑时 `重复` 不能小于 12**。第 1 轮的轮次是 1，剩余 = `重复 - 1`；`重复` ≤ 11
时第 1 轮就命中「剩余 ≤ 10」，变成每轮都重启一次 —— 看着还在跑，实际每轮只发一个
请求，还会不断叠新实例。

日志上：续跑起的是新一份运行，开头又打一遍「=== 文字同步开始 ===」，电脑端按「旧内容
是不是新内容的前缀」判运行，于是会把上一份存成 `ios_shortcut.log.1` —— 正好留下续跑
前那段的痕迹。

**前台 App 名单不在词典里**，它是 `build.py` 顶部的 `APP_LIST`（跟 `TEXT_TYPES` 一样
属于代码常量）：要加一个 App，改那一行再跑一遍 `build.py` + `sign.py`，别去 App 里
手改 —— 手改的那份下次重新签就没了。

名单里的 **`快捷指令`** 是特意留的：在快捷指令 App 里手动点运行时，前台就是它，
不在名单里会被白名单当场挡掉 —— 表现是「点了没反应、日志一个字都没有」。同理，
通过分享菜单、小组件触发时前台不是名单里的 App，也会被挡。

## iOS 权限弹窗

现象（iOS 26/27，同一次运行里，没退出）：

> 允许"文字同步"将 **1 个 app** 和 **1 个文本项目**发送给"192.168.1.23"吗？
> 之前，此快捷指令允许与"192.168.1.23"共享 10 个"剪贴板"项目。
> ［不允许］［显示全部 2 项］［允许一次］［始终允许］

点了「始终允许」，隔几十秒又弹一次。

原因不是写错了，是这类弹窗的计数方式：

- **1 个 app** = 每轮开头那条「获取当前 App」。`app` 属于敏感内容项，系统认为
  「它可能被共享给这个网站」。
- **1 个文本项目** = 这一轮上行 / 拉取时带出去的剪贴板文本。
- 授权是**按内容项实例**评估的，不是按「快捷指令 + 主机」记一次。循环里每轮都
  新读一次 App、新拿一次剪贴板，所以每轮都得重新确认 —— 「始终允许」只对当次生效。
  这也是为什么同一轮循环里能弹几十次。

处理：`前台检查` 默认 **`仅入口`**

| 取值 | 循环里读 App | 弹窗 | 切走 App 后 |
|---|---|---|---|
| `仅入口`（默认） | 不读 | **一次运行只在开头问一次** | 不立刻停，跑完剩余轮次（默认约 160 秒） |
| `每轮` | 每轮读 | 每轮弹一次 | 立刻停（原版行为） |

入口那一次「获取当前 App」省不掉 —— 它就是省电主闸（不在名单里的 App 直接整段
跳过）。所以**做不到完全不弹，只能做到一次运行弹一次**。

其余能减少弹窗的做法：

- `调试` 保持 `关`。开着时每轮多一次 `POST /ios_log`，等于多一份内容项要授权。
- 守卫日志里不再拼「网络的详细信息」（Wi-Fi 词典可能带 SSID），少一类隐私内容。
- **每次重新签名 / 重新导入都会重置授权**，装新包后第一次手动运行还会问一遍，
  点完「始终允许」就不再问 —— 别把它当成「始终允许没用」。
- 想彻底不弹，只能删掉白名单（连开头那次 App 读取也去掉），代价是回到「进任何
  App 都空转」的老样子，不建议。

## 服务端契约

| 接口 | 用途 |
|---|---|
| `POST /ios/sync` | 上行手机内容。body `{key, content, source}`，返回 `{status, latest_global}` |
| `GET /ios/latest` | 纯拉取。`?source=设备名`，请求头 `key`，返回 `{status, latest_global}` |
| `GET /status` | 探活，200 即在线（可达性检查用） |
| `POST /ios_log` | 收 iOS 日志：覆盖写 `log/ios_shortcut.log`；判定为**新一次运行**时先把上一份挪成 `.1` |

判断只看 `latest_global.content` **在不在**，不看 `pasted`：

- 两个接口最终都走 `server/api/flask_app.py` 的 `_take_ios_latest()`，只有「这份
  该投递给本机」的两个分支才带 `content`（且 `pasted` 恒为 `false`，就地
  `mark_pasted` 记账）；没东西时一律是 `{"pasted": true}` 空包。
- `POST /ios/sync` 在「手机发的是新内容」时回的是它自己那份（`content` 与本地
  相同，会被「和剪贴板不同」挡掉），其余情况同样走 `_take_ios_latest()`。
- 所以服务端**不会**给出「带 `content` 但已经投递过」的组合，第三条件
  （原版的 `已粘贴 是 否`）是多余的；拿 JSON 布尔去比中文「否」还很脆 ——
  空值或类型一变就静默失效。

`content` 缺省等于「这次没东西」，不能拿它覆盖缓存 —— 否则同一段文字下一轮会
被当成新内容再上行一遍。

电脑端还有 `text_sync_mode`（双向 / 只发送 / 只接收）的总开关，快捷指令不用管，
它只负责把手机这边的变化报上去、把拿到的写下来。

## 日志怎么读

`调试` = 开 时每轮结束推一次（一次运行 N 轮就是 N 次 POST，每次是全量），服务端
写到 `log/ios_shortcut.log`；判定为新一次运行时，上一份留成 `ios_shortcut.log.1`，
所以「这次不行」还能跟「上次正常」对照。

一次正常的长这样：

```text
=== 文字同步开始 ===
地址 http://192.168.1.23:8000 ｜ 重复 40 ｜ 间隔 3/5/10 ｜ 通知 关 ｜ 续跑 关
设备 iPhone ｜ 白名单 11 个 App
[1] 文本未变 → 拉取
[1] ← 无新内容
[1] 内容相同，不写回
[2] 文本变了 → 上行
[2] ← 有 content
[2] 已写回剪贴板
=== 文字同步结束（40 轮已跑完）===
```

怎么从日志定位：

| 看到 | 说明 |
|---|---|
| 一个字都没有 | 没进白名单：前台 App 不在名单里，或名字对不上（本地化），整段被跳过，一个请求都没发 |
| 只有开始 + 「守卫命中」 | 电量 / Wi-Fi / 可达 三项之一没过；行里带电量实测值和阈值 |
| 停在 `[N] 电脑端不可达，停` | 探活失败：查地址、端口、服务是否在跑、是否同网段 |
| 一直 `文本未变 → 拉取` + `← 无新内容` | 手机没新内容、服务端也没东西可投，链路是通的 |
| 一直 `文本变了 → 上行` | 缓存没落住（`内容Cache` 被别的版本覆盖过），同一段内容在反复上行 |
| `← 有 content` 但没有「已写回剪贴板」 | 内容与剪贴板相同，正常 |
| 有「已写回剪贴板」但剪贴板没变 | 「拷贝到剪贴板」被系统拦了，看快捷指令的通知/权限 |
| 开头地址不是你以为的那台 | 手机上跑的是旧的那份，重新导入 |

日志**不记剪贴板内容**，只记走了哪个分支：内容是隐私，而且长文本会把日志撑爆。
要确认内容本身，去电脑端历史里看。

## 与原版（`下载/文字同步.shortcut`，手工版 90 动作）的差异

原版是手搭的，逻辑对但有一堆绕路和死代码。重构后动作数从 90 涨到 156（多了
守卫拆分、三档等待按真实时长判断、日志、注释），判断路径反而短了：

| 项 | 原版 | 现在 | 为什么 |
|---|---|---|---|
| 时段守卫 | 手机版是 `时间 早于 08:00 或 晚于 23:00`；导出的 plist 里这两个时间被冻成了 `2026-05-24 00:00:15 / 15:00:22`（拖时间控件那天的日期被一起写进去了） | 删掉 | 时段交给自动化的触发条件；导出的那份文件因为日期被冻结，换一天就恒真/恒假，等于随机失效 |
| 每轮探活 | 循环体内每轮 `Is Web Server Reachable`，不是「是」就停 | 同（补回） | 只在入口探一次的话，跑到一半断网时下一条「获取 URL 内容」会抛错中断，那一轮连日志都留不下 |
| 前台 App | 流程最前面「如果 任意一个 App 已打开（10 个）」+ 循环体内「当前 App 没有值就停」 | 同（补回） | **这是省电的主要手段**：只在刷微信、逛浏览器时同步，桌面或别的 App 进去就退、一个请求都不发。名单在 `build.py` 的 `APP_LIST` |
| 等待档位 | `时间1/2/3` 按 `重复索引 < 60` / `< 180` 分档 | 同三档，但按**累计等待秒数**分档 | 索引只到 60：第 1–59 轮走时间1、第 60 轮走时间2、时间3 永远进不去 |
| 读缓存 | 三次「获取存储内容」（第 13、29 条） | 开头读一次 | 同一次运行里缓存不会变 |
| 无用取值 | 第 61 条「获取词典值 pasted」结果没人用 | 删掉 | 死动作 |
| 缓存对齐 | 四条互相重叠的写入：`pasted 有值 且 content 没值`、`远程有值 且 本地≠远程`、`content 有值`、非文本分支直接写整个响应 | 统一成「服务端给了 content 才更新缓存」 | 第一条会把 `{pasted: true}` 空回包盖进缓存 → 下轮拿空串比 → 同一段文字每轮再上行一次（靠服务端回音/去重拦下，白费往返）；最后一条写的是整个响应，`content` 取不到 |
| 缓存内容 | 整份 `latest_global`（`content` + `pasted`） | 一段文本 | 手机端判断只需要「内容」。`pasted` 在服务端已经按设备记在 `clients[source]` 上，再存一份就是两套状态各自漂移 |
| 上行之后 | 只按回包更新缓存，回包是空包时缓存不动 | 上行成功即把缓存记成本地 | 服务端收到就等于「已知这段内容」；不记的话，空回包时下一轮会再上行一次同一段文字 |
| 写回判定 | 一个「全部为真」的三条件（内容有值 / 不是 local / `已粘贴 是 否`） | 两条：有内容 / 和剪贴板不同 | 见「服务端契约」：带 `content` 就等于还没投递，第三条多余；而且它比的是中文「否」对 JSON 布尔，是整套流程最脆的一处 |
| 写回取哪份内容 | 取缓存里的 `content`（`剪贴板内容 = 缓存.content`） | 只取**这一轮响应**里的 `content` | 缓存旧、剪贴板刚变、服务端又没话说时，旧代码会把缓存里的旧内容盖到用户刚复制的东西上 |
| 剪贴板取值 | 剪贴板原对象，直接参与比较与上行 | 另取一份「文本」形态参与比较 | URL / 多信息文本 / 图像各有自己的比较规则，容易比出假差异；文本对文本才稳定 |
| 续跑 | 每轮末尾判 `重复 - 重复索引 ≤ 10`，**没有开关**，无条件自调用（`isSelf`） | 同条件，但加了开关、默认关 | 原版 60 轮里第 50 轮就重启，等于常驻；开关关掉才是「跑完就结束」 |
| 通知开关 | `配置.通知` 是布尔，手机版设成 `False`，条件却写 `是 否` —— 关着反而弹 | `开/关` 文本，判 `是 开` | 原版那条是反的；另外跟「获取同步」的 `调试` 写法保持一致 |
| 日志 | 无 | 复用 `/ios_log`，`调试` = 开 才发 | 排查手段与获取同步一致 |
| 缓存键 | `内容Cache` | 同 | 换名字等于旧缓存读不到，升级后首轮会把旧内容再上行一次（内容形态从词典变成文本，旧缓存读出来只是字符串，最多多上行一次） |
| 触发 | plist 里带 `WFAppInFocusTrigger` + 12 个 App | 不写进产物 | 自动化是手机本地的东西，跟着快捷指令走会互相覆盖 |

## 设计约束（改之前先看这几条）

1. **省电是三道闸，顺序不能反**：先看前台 App 在不在名单（0 个请求）→ 再看电量 /
   Wi-Fi / 可达（1 个请求）→ 最后每轮判「还在这个 App 里吗」。把白名单删掉换成一个
   开关，等于让桌面状态也在轮询，耗电会立刻显出来。
2. **「任一 / 全部」两种多条件都能用，但判断对象不同时才省动作**。`WFAction
   ParameterFilterPrefix: 0` = 任一、`1` = 全部，两者都在原版里出现过（动作 4/22/28
   是任一，动作 36/42/68 是全部），可以直接写。守卫用「任一」三条件、写回用「全部」
   两条件，各一个动作；只有需要「不同走向」时才拆嵌套「如果」。
3. **「有任何值 / 没有任何值」要用表模板，而且 App 类型必须先转文本**。两个坑
   都在真机上复现过：

   - `WFCondition: 100 / 101` 平铺在单条件里，iOS 不认：导入后那条「如果」标红、
     顶部报「请为此操作中的每个参数选取值」，跑到这里整条指令中断。`lib/sc.py`
     的 `if_()` 已经把这两种码自动转成 `WFConditions` 表模板，写流程时照常
     `b.if_(x, ANY)` 即可。
   - 表模板还不够：`获取当前App` 的输出是 **App 类型**的内容项，而 iOS 的条件
     菜单对 App 类型根本没有「没有值」这一项 —— 手动把类型改成文本才选得到。
     所以在判空之前必须挂 `WFStringContentItem` 强转，走 `b.current_app(text=True)`。
     不挂的表现是同一个红框（参数被判空），很容易误判成上一条没修好。

   `verify.py` 的「条件缺参数」兜住第一种回退，`test_app_existence_check_coerces_to_text`
   兜住第二种。
4. **缓存不能空盖**。`{pasted: true}` 这种没有 `content` 的回包如果盖上去，
   下一轮剪贴板里那段文字就会被判成「手机刚复制的」再上行一遍。反过来，上行
   成功之后必须把缓存记成本地：服务端已经收下了，不记就每轮都重发。
5. **写回只用两条判据**：有 `content`、和剪贴板不同。不要再加 `pasted` —— 带
   `content` 就意味着还没投递，服务端不会给出「带 `content` 但已投递」的组合
   （见「服务端契约」）。少了「不同」这条，用户刚复制的东西会被上一份内容盖回去；
   而判断用的 `content` 必须来自**这一轮响应**，不能取缓存里的那份，否则会拿旧
   内容盖新剪贴板。
6. **轮询里不弹进度通知**。「获取同步」是人工触发、一次跑完，弹进度没问题；
   文字同步每 3 秒一轮，弹进度会把通知中心刷爆。只有真正写回剪贴板时才弹
   （且还要 `通知` = 开）。
7. **探活不能换「获取 URL 内容」**。那条动作连不上时直接抛错并中断整条指令，
   而守卫要的恰恰是「连不上就安静退出」。探活本身是一次额外请求：入口一次、
   之后每轮一次 —— 40 轮就是 41 次 `/status`，这是原版也付的成本，别再加。
   它的参数形状要照 Actions 自己导出的样子写（`host` 是文本 token、`timeout`
   是字符串 `"3"`），类型不对时 App 里那句参数会显示成空白、跑起来恒判不可达。
8. **`时间1~3` × `重复` 别超过后台时长**。默认 40 轮 ≈ 20×3 + 20×5 = 160 秒，
   落在系统给后台运行的时间里，只用得到前两档；想更久就开「续跑」（每续一次都
   重新过一次守卫），别硬调大 `重复` —— 被系统掐断时既没有收尾日志也没有续跑。
   真要让第三档（10 秒/轮）生效，得把 `重复` 调到 45 轮以上，那时总时长会
   明显超过 3 分钟，只在「插着电长时间驻留」的场景下值得。

## 已知限制

- **依赖 Actions**（`IsReachableIntent`）做探活。没装这个 App 的话，守卫里的
  「服务是否可达」会报「找不到 App Intent」，把那一整段守卫换掉或删掉即可。
- **断网会停在这一轮**。每轮开头先探活，不可达就记一行日志后停。代价是那一次
  `/status` 自带 3 秒超时，网络差时会拖慢轮次；把 `时间1` 调大能减少探测次数。
- **时段守卫没了**。原版靠 `08:00–23:00` 限制夜间不跑；现在只靠自动化的触发
  条件。要恢复夜间停跑，最省事的办法是在自动化里再加一个「时间在 08:00 到
  23:00 之间」的条件，别把日期比较塞回快捷指令（导出时会把日期冻结，见上表）。
- **「有 content 就等于待投递」依赖服务端实现**。这条是从 `flask_app.py` 的
  `_take_ios_latest()` 读出来的：只有投递分支带 `content`。哪天服务端改成
  「投递过也回 content，只是 `pasted` 不同」，快捷指令这边要跟着把 `pasted`
  的判据加回来 —— `tests/test_smoke_e2e.py::TestIOSPollProtocol` 就是拿真
  `TextTracker` 跑这个判断的，改服务端时它会先炸。
- **App 名字是本地化的**。白名单里的 `文件 / 信息 / Safari浏览器 / 备忘录` 都是中文
  系统下的叫法，换语言就全部对不上，结果是「永远不进白名单」—— 改语言前先改
  `build.py` 的 `APP_LIST`，而且要和自动化里选的那批 App 一致（手动运行靠名单里的「快捷指令」）。
- **项目类型名是本地化的**。判断剪贴板是不是文本靠 `文本 / URL / 多信息文本`
  三个名字；系统语言不是中文时，这三个字符串对不上，会一律走「非文本」分支
  （只拉取、不上行）。改语言前先改 `build.py` 里的 `TEXT_TYPES`。
- **续跑用的是「调用自己」**。若 iOS 在开启后提示找不到快捷指令，在编辑器里把
  这个动作重选一次「文字同步」即可；默认关着，不影响主流程。
- 自动化的位置：快捷指令 App → 自动化 → 个人自动化 → App → 打开时 →
  选常用 App（微信 / 浏览器 / 备忘录…）→ 运行「文字同步」，并关掉「运行前询问」。
