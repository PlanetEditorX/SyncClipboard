# iOS 快捷指令：推送同步

把手机上的东西**主动**推到另一台设备上去 —— 分享面板里选这条指令，分享过来的
文件直接落到目标设备的保存目录；桌面上点它，推的是剪贴板（文字进电脑剪贴板，
文件走上传）。

跟另外三份的区别就一句话：那三份都是「等」——等你去复制、等自动化触发、等开 App；
这份是「现在、就这一个」。

## 两种用法

| 入口 | 内容来自 | 走哪条路 |
|---|---|---|
| 分享面板（照片 / 文件 / 浏览器 / 微信…） | 分享进来的文件，可以多个 | 选目标设备 → 逐个 `PUT` 上传 |
| 桌面图标直接点 | 剪贴板 | 文本 / URL → `POST /ios/sync`，电脑剪贴板里直接粘；文件 / 图像 → 上传 |

## 它和另外三份的分工

| | 触发 | 方向 | 推什么 |
|---|---|---|---|
| 获取同步 | 手动点 | 电脑 → 手机 | 电脑上的文件 / 目录 |
| 文字同步 | 「打开 App 时」自动化，驻留轮询 | 双向 | 剪贴板的变化，只在白名单 App 前台时跑 |
| 短信同步 | 「收到信息时」自动化 | 手机 → 电脑 | 验证码 |
| 推送同步（本份） | 手动一次 | 手机 → 选中的那台设备 | 你手上这一份：文件，或者剪贴板 |

想「现在就把这个文件推过去」，只有这份能做到：文字同步推的是剪贴板的变化、而且
只在它驻留时才动；短信同步只认验证码。

## 原来那份草稿的问题

草稿是手搭的 66 个动作，能跑但很脆。下面每一条都在导出的 plist 里核过。

| # | 位置 | 问题 | 后果 |
|---|---|---|---|
| 1 | 配置词典（动作 1） | `主机` 写死 `192.168.1.24` | 那是更早的地址；现在默认是 `192.168.1.23`，照抄等于全链路连不上 |
| 2 | 动作 7 的注释 + 动作 8 | 注释写「获取当前app，如果没有值说明在桌面，停止运行」，可那个「获取当前App」的输出**在全文件里被引用 0 次** | 守卫不存在。在桌面点、或别的指令调它，都会照跑一遍，还会弹一次权限框 |
| 3 | 动作 0 设的 `文件名` | 赋的是 `输入.File Path`，这个变量**一次都没被用过** | 死变量；真名其实在后面用 `URL编码(文件)` 另算了一遍 |
| 4 | 动作 14–42 与 44–65 | 两段几乎逐字相同：查在线 → 选设备 → 循环 → PUT | 改一处忘一处。两条分支的文件名规则就已经不一致：一条是 `{编码(项目)}_{序号}.{项目}`，另一条只有 `{编码(项目)}`；而且**两种都拿不到真扩展名** —— 文件文本化给的是不含后缀的 Name |
| 5 | 整条没有判空 | 剪贴板空着也照发 | `POST` 空 `content`，服务端回 400，快捷指令显示成「无法连接到服务器」——看起来像网络问题 |
| 6 | 动作 19 | 文字走 `POST /text_sync` | 跟文字同步、短信同步走的不是同一条通道（那两份用 `/ios/sync`）。服务端对 iOS 的投递记账在 `/ios/sync` 那条路上，混着用排查时会对不上 |
| 7 | 整条没有日志 | — | 出问题手上什么都没有：不知道停在哪一步、回包是什么 |
| 8 | 通知文案（动作 22/45） | 「正在查询在线客户端」挂在 `获取剪贴板类型` 的输出上 | 标题区显示的是「文本 / 图像」，不搭 |
| 9 | 通知文案（动作 35/58） | 「正在上传第 N 个文件」 | 没有文件名；多文件时只能靠数 |
| 10 | `通知` / `调试` | 没有开关 | 想静默跑只能删动作 |

另外三条不是 bug，但这次一并改了：

- 查在线设备时带上了 `?source=`（URL 编码后的设备名），服务端能把「来问的设备」
  顺手登记，也不会把 iOS 自己列进去。
- 客户端列表回包先看 `status`：密钥错时服务端回 `{status: error, message: 密钥错误}`，
  原版会把它显示成「没有客户端在线」，让人白去开电脑端。
- 「没有客户端在线」保留**模态提示**（原版也是 alert），不改成通知：你刚在分享面板
  点完，静默退出跟没点动没区别。

## 重构后的流程

```text
内容 = 快捷指令输入（有分享输入）或 剪贴板（从图标点开）
  └ 内容是空的 → 记日志 → 停
探活 /status
  └ 不可达 → 记日志 → 通知(可选) → 停
类型是 文本 / URL / 多信息文本？
  ├ 是 → POST /ios/sync {key, content, source}
  │        └ status = ok → 通知「已推送到电脑（N 字）」→ 日志
  │        └ 其它        → 通知失败原因 → 日志
  └ 否 → GET /clients/online?source=<编码后的设备名>
           └ status ≠ ok → 模态提示「服务端拒绝了这次请求」→ 停
           └ 没有在线客户端 → 模态提示 → 停
           └ 选一个目标 → 逐个 文件：
                名称   = URL编码(文件)           # 直接编码，不经文本中转
                点后缀 = 扩展名有值 ? ".ext" : ""
                PUT {上传地址}?filename={名称}{点后缀}  key/source/target/...
                日志记一行
           └ 通知「已推送 N 项到 X」
```

152 个动作（含注释与日志分支）。数多是因为每条日志都是「文本 + 设定变量 + 如果
调试开 + POST」四五个动作，不是判断绕：真正出网的三处（探活 / 推文字 / 列设备 +
上传）一眼能数出来。

### 几个刻意的取舍

| 决定 | 为什么 |
|---|---|
| 用「输入有没有值」判场景，不看前台 App | 分享面板是独立进程，跑到这里时前台未必还是原 App；「有没有输入」才是这件事的真判据（也顺手替掉了原版那个没接线的守卫） |
| 文字推 `/ios/sync` | 跟文字同步、短信同步同一条通道；`source` 用同一个设备名，服务端才认得出这是同一台手机 |
| 不做暂存、不重试 | 文字同步那种暂存是为「人不在也没关系，回头补」；这条是你手动点的，人和内容都在场，推不上去当场说清楚、再点一次更省事 |
| 探活用 Actions 的 App Intent | 用「获取 URL 内容」探活时连不上会直接抛错中断整条指令，弹的是「无法连接到服务器」，分不清是没开机还是密钥错 |
| 上传是一次循环里一个 PUT | 原版两段复制；一份流程意味着文件名规则、请求头、日志只有一处要改 |
| 「没有客户端在线」用 alert 而不是通知 | 通知会自己消失、还可能被专注模式吞掉；手动触发却毫无反馈最难受 |
| 日志不记内容 | 只记字数、类型、目标、每项结果。推的内容可能是私人文件，日志会落到电脑端磁盘上 |
| 名称直接 `URL编码(文件)`、后缀单独拼 | 文件变量一旦先进「文本」动作，中文 UTF-8 会被按 GBK 读成乱码；后缀是纯 ASCII，接在 URL 末尾即可，PUT 仍只有一处 |
| 服务端再兜一层乱码还原 | 兼容旧版指令 / 别的客户端发来的 GBK 误读文件名；只在能还原成合法 UTF-8 时改写，不误伤正常中文 |
| 文字用 `Characters` 计数 | 「计数」缺省数的是项目数，一段文字恒为 1；通知里的「N 字」要显式切到字符数 |

## 配置词典

导入后点「配置」直接改，改完不用重新签。全是**文本**：写成数字/布尔，在「如果」
里会显示成空白，判据恒不成立。

| 键 | 默认 | 说明 |
|---|---|---|
| `协议` | `http` | 拼地址 `协议://主机:端口` |
| `主机` | `192.168.1.23` | 中心服务地址，与 `config/server_config.json` 的 `host` 一致 |
| `端口` | `8000` | 中心服务监听端口 |
| `密钥` | `123456` | 与电脑端一致；进请求头 `key` 和 body `key` |
| `通知` | `开` | 开 = 结果各弹一条；关 = 只留日志（模态提示不受它管） |
| `调试` | `关` | 开 = 每次运行把日志 POST 到 `/ios_log`，覆盖写电脑端 `log/ios_shortcut.log` |

## 服务端契约

| 接口 | 用途 |
|---|---|
| `GET /status` | 探活，200 即在线 |
| `POST /ios/sync` | 推文字。body `{key, content, source}`，回 `{status, latest_global}` |
| `GET /clients/online` | 问在线设备。`?source=` 是 URL 编码后的设备名；回 `{online_clients: [显示名…], upload_url: {显示名: 地址}}` |
| `PUT <upload_url>` | 上传文件。`?filename=`，请求头 `key` / `source` / `target` / `Content-Type`，body 是文件二进制 |
| `POST /ios_log` | 收日志（调试 = 开） |

除 `/status` 探活外，**每个请求都必须带 `key` 请求头**。服务端与电脑端 FileServer 共用同一个 `require_key()`：请求头是唯一契约，JSON body 里的 `key` 与 `?key=` 只是等价入口。漏带 `key` 拿到的是 403 `{status: error, message: 密钥错误}`，弹出来像「密钥配错了」，实际是那条请求没带钥匙，文件分支整个走不通。

`upload_url` 由服务端按目标类型给，手机这边照用不辨类型：

| 目标 | upload_url | 谁的 `/upload_file` 收 |
|---|---|---|
| 电脑（Windows / Linux 客户端） | `http://<电脑>:<端口>/upload_file` | 那台电脑自己的客户端，`filename` 取最后一段做纯文件名 |
| Android | `http://<服务端>/upload_file_to_download?redirect=http://<安卓>:<端口>/upload_file` | 先落到服务端 `save_path`，再由服务端通知安卓来下载 |

Android 那条的地址本身已经带了 `?redirect=`，快捷指令再拼 `?filename=` 就变成
`…?redirect=http://ip:port/upload_file?filename=x` —— 看着像拼错，实际是把
`filename` 塞进了 `redirect` 的值里，服务端 `parse_qs` 解出来的 `redirect` 正好
是 `http://ip:port/upload_file?filename=x`，再解析一次就拿到文件名。所以两种目标
都只需要在自己这一层拼一次 `?filename=`，不用分叉。

`source` 用**设备名**，和文字同步 / 短信同步同一个：服务端按 `clients[source]` 记
「这台设备手上是哪份内容」，同名才认得出是同一台手机。中文设备名要先 URL 编码再
进请求头（客户端读 `source` 时不按 UTF-8 解）。`target` 是给人看的显示名，只进
服务端 / 电脑端的日志，不参与存储。

## 文件名从哪来

iOS 把文件强制转文本时给的是 **Name 属性，不含扩展名**；而且**不能先把文件变量
塞进「文本」动作再编码** —— 真机上那一步会把 UTF-8 字节按 GBK 读，
`SEXJ62_证书文件(密码1)` 落盘成 `SEXJ62_璇佷功鏂囦欢(瀵嗙爜1)`、`飞牛下载`
变成 `椋炵墰涓嬭浇`。正确形状是**直接编码文件变量**，后缀单独拼在 URL 末尾：

```text
名称   = URL编码(文件)                     # 中文 / 空格 / # 都安全
扩展名 = 文件扩展名(文件)                  # 不带点，如 shortcut / png
点后缀 = 扩展名有值 ? "." + 扩展名 : ""     # 纯 ASCII，不参与编码
PUT     ?filename={名称}{点后缀}
```

URL 编码动作显式写了 `WFEncodeMode = Encode`（它还有个 Decode 模式）。后缀来自
系统属性、是纯 ASCII，直接接在编码后的名称后面即可；取不到时不拼点号，免得把
文件存成 `a.`。

服务端还有一层兜底：`common/utils.py::fix_mojibake_filename()` 接在
`client/file_server.py::upload_file`、`server/api/flask_app.py::upload_file` 和
`upload_file_to_download` 三处文件名解码之后，把「UTF-8 被按 GBK 读」的乱码名
还原回来。它只在字符串按 GBK 编回去恰好是合法 UTF-8、且还原后更短时才改写，
正常中文 / 纯 ASCII 不受影响（`tests/test_utils.py` 有用例）。**已经落盘的乱码
文件不会自动改名**，需要手动重命名。

- 分享面板进来的文件有 Name 也有 File Extension，落下去就是原名带后缀
  （推送 `推送同步.shortcut` 就存成 `推送同步.shortcut`）。
- **剪贴板里的图像 / 从相册拷贝的图**既没有 Name 也拿不到 File Extension，会
  退化成服务端的 `uploaded_file` 或 `Image`。这是 iOS 的限制，不是漏写；介意的
  话先在「文件」App 里存成文件再分享过来。
- 同名文件覆盖：电脑端 `open(path,'wb')` 直接盖，不会存成「a 1.png」。

### 边界：压缩包解压出来的中文乱码，不归快捷指令管

服务端是 `request.get_data(as_text=False)` → `open(path, 'wb').write(file_data)`：
**整个压缩包按字节原样落盘，包内条目名一个字节都不会碰**。上面那个
`fix_mojibake_filename()` 也只修 URL 查询串里的 `filename=`（压缩包自己的名字），
够不到包内条目。所以「压缩包名字正常、解压出来的文件名乱码」是两层不同的事。

ZIP 规范用 general purpose bit 11（`0x800`）标记条目名是 UTF-8；没设这个位时，
解压器按本地 ANSI 代码页解读。手机 / macOS 的压缩工具常写 UTF-8 字节却**不设**
这个位，而 Windows 资源管理器内置的「压缩文件夹」一律按 GBK/CP936 读，于是
`测试` 变成 `娴嬭瘯`。换任何传输方式（AirDrop、微信、U 盘）都照样乱码 —— 这条
对照实验一做就能排除快捷指令。

解法在解压侧：用 Bandizip（勾「强制 UTF-8 文件名编码」）或 WinRAR（解压对话框
里的「文件名编码」）解压，别用资源管理器双击；或者手机端改用 `.7z` / `.tar`
（内部固定 UTF-8，没有这个坑）。已经落盘的乱码条目名可按
`name.encode('gbk').decode('utf-8')` 反编重命名，跟上面同一个函数。

## 日志怎么读

`调试` = 开 时每次运行推若干次（空内容 / 不可达 / 推完各一次），写进电脑端
`log/ios_shortcut.log`。一次正常的长这样：

```text
推送同步日志（构建 2026-11-23 11:20）
=== 推送同步开始 ===
地址 http://192.168.1.23:8000 ｜ 来源 分享 ｜ 类型 文件
设备 iPhone ｜ 数量 2
⑥ 目标 DESKTOP-ABC (192.168.1.40) ｜ 待传 2 项
  · 第 1 项：文件上传成功
  · 第 2 项：文件上传成功
=== 推送同步结束 ===
⑥ 全部上传完成
```

| 看到 | 说明 |
|---|---|
| 一个字都没有 | `调试` 还是关；或没点到这条指令（分享面板里选错了） |
| 「没有内容可推（来源：剪贴板）」 | 从图标点的，但剪贴板是空的 |
| 「服务端不可达」 | 地址 / 端口 / 同网段 / 服务有没有在跑（先看 `GET /status`） |
| 「客户端列表请求失败：error / 密钥错误」 | 「配置」里的密钥与电脑端不一致 |
| 「没有在线客户端」 | 电脑端没开，或不在同一网段。iOS 不会出现在这个列表里（它只能轮询） |
| 「第 N 项：密钥错误」 | 走到上传才失败：中心服务的密钥对，但目标设备的密钥不对（两台设备各有一份配置） |
| 文件落了但名字是 `uploaded_file` | 剪贴板里的图没有名字，见上一节 |
| 文件名是 `璇佷功鏂囦欢` 一类乱码 | UTF-8 被按 GBK 读。当前版本已双层修复；旧版本落盘的文件不会自动改名，需手动重命名 |
| 压缩包名字正常、但**解压出来**的中文名乱码 | **与快捷指令无关**：ZIP 条目名编码 + Windows 内置解压器按 GBK 解读。换 Bandizip / WinRAR 并指定 UTF-8 解压，见上一节末尾 |

`ios_shortcut.log` 是**三份快捷指令共用**的一份：文字同步、短信同步、推送同步都往
它写。服务端 `/ios_log` 按「新内容是旧内容的前缀」判定是不是同一次运行，是就覆盖，
不是就把上一份挪成 `.1`。所以看到的内容可能是上一条指令留下的 —— 首行的
「（构建 …）」和标题行能区分。

## 构建

```bash
python shortcuts/推送同步/build.py                                        # 生成 plist
python shortcuts/lib/verify.py shortcuts/推送同步/推送同步-unsigned.plist
python shortcuts/lib/sign.py shortcuts/推送同步/推送同步-unsigned.plist
python -m unittest tests.test_smoke_e2e.TestPushSyncArtifact -v            # 产物约束（12 例）
```

当前产物：152 个动作，断裂引用 `none`，控制流异常 `none`，可疑参数 `none`，
条件缺参数 `none`；全量回归 `376 tests OK`。

`TestPushSyncArtifact` 锁的是最容易退化、又最难在电脑上看出来的几件事：
`ActionExtension` 与「快捷指令输入」的声明（少了就没有分享入口）、上传必须是
`WFHTTPBodyType = File` + `WFRequestVariable`（少一个服务端收到空 body）、
`filename` 必须是 URL 编码动作的输出（顺着变量反查）、文字只走 `/ios/sync`、
循环与上传各只有一处、不许把那个没接线的「获取当前App」抄回来、每个出网请求
都得带 `key` 请求头（漏在 `/clients/online` 上会伪装成「密钥错误」）、文件名链
必须同时拼上「名称」和「点后缀」、名称不许经「完整名」文本中转（中文会变 GBK
乱码）、文字通知的字数必须来自 `Characters` 计数（否则恒显示「1 字」）、探活必须
排在所有出网动作之前而判空又
排在探活之前。

## 已知限制

- **依赖 Actions**（`IsReachableIntent`）探活。没装这个 App 的话，把那一步换成
  「获取 URL 内容」打 `/status`，代价是电脑没开时那一步会抛错中断（后面的通知与
  日志都没有了）。
- **一个目标设备，单选**。要一次推给多台，得把「从列表中选取」改成多选，后面的
  上传地址取值与循环都要跟着改（不是只勾一个开关）。
- **只有一层目录**：分享一整个文件夹时，iOS 传进来的是目录本身，上传按文件读，
  子结构不会保留。要整目录，用「获取同步」那条反向拉。
- **大文件没有进度**：`PUT` 是一次性的，几百 MB 的视频会静默等很久（分享面板里
  那条指令会一直转圈）。
- **iOS 设备不能作为目标**：`/clients/online` 会主动跳过 iOS/iPhone/iPad —— 它们
  只能轮询，没法被直传。两台 iPhone 之间互推这个需求，得靠「都推给电脑、再从
  电脑拉」间接实现。
- **剪贴板图像可能拿不到扩展名**：「获取文件的详细信息」针对文件类内容项，
  图像输入可能返回空；此时不拼后缀，落盘名退化成 `Image` 或 `uploaded_file`。
  若真机在这条路径上报类型错误而中断，需把该步输入先强制转成文件类型。
- **重签会重置权限**：每次重新导入都要重新允许「访问网络」与「访问剪贴板」。
